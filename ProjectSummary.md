# Project Summary

Evolv.io is a Swift reimplementation of Karl Sims' 1991 SIGGRAPH paper "Artificial Evolution for Computer Graphics." The original paper describes a system where symbolic Lisp expressions (genotypes) are evaluated per-pixel across a 2D grid to produce procedural images (phenotypes) — think of it as a tree of math/image operators (+, log, round, color blends, noise functions, etc.) that, when evaluated at every (x, y) coordinate, paints a picture. Evolution (selection/mutation/crossover of these expression trees) is the long-term goal, but the current phase is about faithfully reconstructing the evaluator itself.

The core problem: Sims' paper lists the function names used in his example genotypes (invert, round, log, color-grad, rotate-vector, bump, etc.) but does not give precise mathematical definitions for most of them — the CM-2/Lisp implementation was never published in enough detail to know exactly what each operator computes. So for any given primitive, there are usually multiple plausible interpretations (e.g., is invert a color inversion 1-v or a numeric reciprocal 1/v? Is round snapping to a grid or doing integer division? Does log preserve sign or take absolute value first?), and the only way to figure out which one Sims actually used is to guess an implementation, evaluate one of his published example expressions with it, and compare the rendered output against the actual figure from the paper.

Why this is hard: the published example genotypes (Figures 5, 9, 10, etc.) are deeply nested expressions where these ambiguous primitives are composed many layers deep — an operator's behavior can dramatically change the shape of the final image, and a wrong guess about one primitive can be partially masked or amplified by others downstream. There's no ground truth for the intermediate values, only the final rendered pixels to compare against a scanned image from a 30-year-old paper. So the project is fundamentally a black-box reverse-engineering exercise: propose a candidate definition for an operator, render, visually diff against the reference figure, and infer from the discrepancy which operator (or combination of operators) is likely still wrong.

Current state: a handful of these ambiguous primitives have plausible-but-unconfirmed implementations, and none of the reconstructed reference figures are yet a close visual match to the paper — some structural elements (large-scale shapes, symmetry, boundary curves) are still substantially different from the originals, indicating at least one more core primitive is still defined incorrectly.

## Rendering architecture: Metal-only, compiled from the expression tree

Rendering is not a per-pixel Swift interpreter walking the `Node` tree at runtime. Each `Node` implements `_emitMSL(into: MSLCodegenContext) -> String` (`ExpressionTree/Node.swift`), which emits Metal Shading Language expression text for that node given its children's already-emitted variable names. Walking a tree once (`codegenMSL`) produces the full body of a compute kernel — the tree shape is compiled to MSL source, and *that* is what runs per pixel on the GPU, not Swift.

- **`MSLCodegenContext`** (`ExpressionTree/MSLCodegen.swift`) accumulates emitted statements and memoizes by node identity (`ObjectIdentifier`), so a node instance referenced more than once in a tree (e.g. a shared sub-expression) emits its MSL only once. It also tracks which shared preambles a tree needs (Perlin noise table, lighting helper functions) via `MSLResourceRequirements`, and supports `emitFunction(for:)` to compile a subtree into a standalone MSL function — used by nodes that need to sample a subtree at offset coordinates (e.g. finite-difference gradients in `GradientDirection`/`ColorGradient`/`ColorGradientCurvature`).
- **`MetalRenderContext`** (`ExpressionTree/MetalRenderContext.swift`) is a process-wide singleton owning the `MTLDevice`/`MTLCommandQueue` and a compiled-pipeline cache keyed by `node.toString()` (the tree's structural fingerprint) plus any live-tunable statics baked into the generated MSL as literals (`ColorGradient`/`ColorGradientCurvature`'s debug delta/heightFactor/lightZ/tapCount — not yet promoted to real uniforms, so changing them still triggers a recompile rather than just a buffer update). It builds the full render kernel (coordinate mapping, supersampling, NaN/infinity sanitizing) around the codegen'd tree body.
- **`Evaluator`** (`ExpressionTree/Evaluator.swift`) is now a thin wrapper: `render(node:scale:supersample:)` just forwards to `MetalRenderContext.shared.render(...)`. `NodeRenderer` calls this to produce its pixel buffer, same public API as before.
- There is no CPU fallback and no Swift per-pixel evaluator anymore — the original `ExpressionResult`/`CachedNode`/per-node `evaluate(using:)` machinery was deleted once every node type had MSL codegen coverage. `NodeDebuggingView`'s hover inspector was rebuilt to do a nearest-pixel lookup into the already-rendered buffer instead of live-evaluating at an arbitrary coordinate.

This was a deliberate performance-driven rewrite (a hand-ported benchmark of Figure 9 measured Metal at roughly two orders of magnitude faster than the Swift path cold, three orders of magnitude warm, at full render resolution), not an incremental optimization — the tradeoff accepted is that debugging/tuning a node's math now means reading or logging generated MSL rather than stepping through Swift.
